# Chess Workbench: product, workflow and technical review

19 September 2026 · Reviewed checkout `152d896` · Diagnosis only

Chess Workbench has a credible technical foundation, but its learning workflow is incomplete. It can find a position worth investigating, report engine output and list facts about the board. It does much less to help the player investigate that position, understand the consequence of a decision, or retain what they learned. Its most damaging interaction is that trying an alternative move removes the game being reviewed and its analysis.

The next investment should be one complete learning session, not another independent analysis panel. My recommended product hypothesis is: **bring a game, understand one or two consequential decisions, try alternatives without losing context, and leave with a useful takeaway.** Keep standalone position exploration as a secondary entry point using the same investigation tools. Validate that choice with the owner before making game review the permanent centre of the product.

## 1. What is it actually trying to do?

The user job is to turn a chess position they care about into understanding they can use in their next game. The user already has access to moves and engine scores; the missing value is deciding what deserves attention, seeing why it matters, testing their own reasoning and remembering the lesson.

There are three overlapping ambitions in the repository:

| Ambition                                      | Evidence                                                                                              | Current delivery                                                                |
| --------------------------------------------- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| A personal position-understanding instrument  | [Product vision](/home/carl/projects/chess-workbench/docs/product.md), especially sections 1, 3 and 7 | Legal board, FEN, one engine line, material and static loose-piece observations |
| A review tool for learning from games         | [Milestones 6–9 in the journal](/home/carl/projects/chess-workbench/docs/journal.md)                  | PGN main-line navigation, batch analysis and three review moments               |
| A project for learning modern web development | Product document section 2                                                                            | A working deployment, sensible boundaries and substantial executable tests      |

The third ambition has progressed further than the first two. That is a legitimate achievement, but completing technical milestones is not evidence that the owner now has a reason to open the application after playing chess.

The implemented product is currently a **session-only analysis board with a game-review shortlist**. It is not yet an explanatory coach or a system for recognising recurring mistakes. The broad intention in `AGENTS.md` includes patterns across games, but the implementation has neither retained games nor retained lessons. That gap should inform product direction without turning into an immediate requirement for a database or training platform.

### Reason to exist beside existing tools

Finding mistakes and offering better moves is already established functionality. Lichess's official description documents reviewing mistakes, retrying moves, exploring continuations and using imported games. Chess.com's current mobile help documents explanations, showing continuations and retrying decisions. These are capability baselines, not a claim that their entire experience suits this owner. Sources: [Lichess: Learn from your mistakes](https://lichess.org/@/lichess/blog/learn-from-your-mistakes/WFvLpiQA), [Chess.com: Game Review on the app](https://support.chess.com/en/articles/10328363-how-do-i-use-game-review-on-the-app), accessed for this review. The Lichess article is historical; I have not performed a current full competitor usability study or compared subscription limits.

Therefore “Stockfish plus plain-English observations” is not enough differentiation. A plausible reason to choose Chess Workbench is a particularly clear, controllable investigation of the owner's own questions, with evidence visible on the board and useful personal takeaways. Local computation and no account are benefits, but do not compensate for extra work to understand a move.

Do not assume even that hypothesis is correct. If the owner's recurring need is instead “I understand the game until this one mysterious engine move,” prioritise a position investigation tool and reduce emphasis on whole-game scanning. If neither workflow improves on the owner's existing tools, keep this as a learning project rather than expanding its feature list to manufacture a product rationale.

## 2. Evidence and review method

I inspected the README, product and architecture documents, journal, milestone specifications, application components, domain and engine logic, tests, build configuration and git history. The public GitHub issues endpoint returned an empty list for all states on the review date; there was no issue discussion to use as user evidence.

I ran the deployed app and the current checkout with real Stockfish. Desktop inspection included the initial screen, PGN import, batch analysis, selecting moments, navigating before/after positions, switching views, dragging an alternative and reloading the retained PGN. I also inspected narrow-screen game navigation at a requested viewport width of 390 pixels. The local run reproduced the key explanation mismatch described below. These were diagnostic examples, not observation of the owner using their real games.

Reproduction game:

```pgn

[Black "Black example"]
[Result "0-1"]

1. f3 e5 2. g4 Qh4# 0-1
```

The quick pass correctly singled out `2. g4` as allowing mate. Selecting it showed the board **after** `g4`, alongside an engine line starting **before** it with `2. e4`. Position details showed `2... Qh4#`, but also “No tracked material, check, or loose-piece status changed,” equal material and no loose pieces. This is a particularly simple case where the parts work while the overall explanation fails.

Confidence labels below separate observed/code-established behaviour from hypotheses about its importance to this particular owner. No claim about retention or chess improvement has been measured.

## 3. Significant problems, in priority order

### 1. Exploration destroys the review context

**Type:** workflow/UX problem encoded in the state model. **Confidence:** high.

**Evidence:** In the browser I moved back to the position after `1...e5` and dragged `g2–g3`. Game navigation, the selected review moment and retained evaluations disappeared. The PGN text survived, but loading it again returned to the start with “Analyse game.” [App.tsx](/home/carl/projects/chess-workbench/src/App.tsx:34) permits either a standalone FEN or an imported game; `commitMove` calls `commitPosition`, replacing the workspace. [App.test.tsx](/home/carl/projects/chess-workbench/src/App.test.tsx:547) explicitly expects a legal board move to exit review. The engine hook clears results when game identity changes. Standalone mode also retains only the latest FEN/report, without undo or a navigable exploration line.

**Effect:** The natural learning action—“what if I played this?”—costs the user their place and analysis. It discourages experimentation and makes following even the provided engine line awkward. A small exit warning at the bottom of the panel does not make this a suitable interaction.

**Direction:** Retain the imported game and selected source ply while exploring a temporary line. Provide undo/redo, reset to the line root and an explicit “Return to game” action. Preserve review results throughout. Start with one temporary line, not a general variation-tree editor. Give standalone positions the same small history mechanism.

**Validation:** The need for reversibility is clear. Validate whether one temporary line is sufficient before building saved branches or comparison trees.

### 2. Findings stop where understanding should begin

**Type:** underlying product gap, with presentation consequences. **Confidence:** high for the gap; the best teaching format needs validation.

**Evidence:** [ReviewMomentsPanel.tsx](/home/carl/projects/chess-workbench/src/components/ReviewMomentsPanel.tsx:76) describes score loss or a mate transition. It does not explain the chess mechanism. [PositionChangesPanel.tsx](/home/carl/projects/chess-workbench/src/components/PositionChangesPanel.tsx) only covers material, check and static loose-piece transitions. [PositionInsightsPanel.tsx](/home/carl/projects/chess-workbench/src/components/PositionInsightsPanel.tsx) gives material inventories and attack-map warnings. The `g4` example above demonstrates how these observations miss the salient consequence even when Stockfish supplies it.

**Effect:** The user still has to do the hardest work: connect the evaluation change to a concrete threat, understand why their move permits it and decide what to notice next time. More factual observations would not necessarily solve that integration problem.

**Direction:** Organise the review around one question: “What did this move allow, and what could I do instead?” Show the played move, an inspectable opponent response and an alternative from the pre-move position. Link a short explanation to those board states. For the example, show `...Qh4#` and the now-open route towards the king; explain only facts that the implementation can establish. Put material and loose-piece details underneath as supporting observations. Where no explanation is supported, say so and offer line exploration.

Do not jump straight to an LLM. A fluent paraphrase of the existing disconnected facts can still fail to explain the position. First make evidence replayable; then test whether a narrow deterministic explanation, human-written prototype or grounded language layer adds value.

**Validation:** Use tactical and quiet positional examples from the owner's games. Can they explain the consequence in their own words afterwards? If they can already read SAN and infer the reason quickly, invest more in comparison and less in prose.

### 3. Review selection optimises score deterioration rather than this player's learning

**Type:** product/selection policy. **Confidence:** high about current rules; medium about the best replacement.

**Evidence:** [reviewMoments.ts](/home/carl/projects/chess-workbench/src/analysis/reviewMoments.ts:31) considers both players, admits losses of at least 75 centipawns, ranks mate categories first, sorts other losses by size and keeps three. There is no player-side preference, teaching relevance, grouping of related decisions or reviewed state. The mate-distance restraint and FEN matching are sensible safeguards, but they do not establish learning value.

**Effect:** Opponent errors can occupy the whole shortlist. Several moments can describe one already-decided game, while a smaller but understandable decision disappears. A hypothetical loss from +10 to +6 outranks a loss from +0.5 to −1.5 under the ordinary numeric rule, even though the second may be more useful to review. This is an implication of the algorithm, not an observed frequency in the owner's games.

**Direction:** Add “I played White / Black / Both,” then filter before selecting the shortlist. Keep “Both” for master-game study. Offer manual “Review this move” so an engine threshold cannot veto the user's question. Evaluate a small candidate-ranking change on actual games: prefer consequential, distinct decisions and avoid redundant moments. Keep selection separate from factual engine output.

**Validation:** Have the owner rank useful moments in roughly ten recent games before tuning thresholds or adopting a win-probability formula. Ask whether missed opportunities, defensive choices or repeated habits matter most. An automatically selected top three should be a starting point, not the entire product definition.

### 4. The interface follows feature boundaries rather than an investigation

**Type:** workflow and information hierarchy. **Confidence:** high.

**Evidence:** [GameReviewPanel.tsx](/home/carl/projects/chess-workbench/src/components/GameReviewPanel.tsx) puts the shortlist and main line in Review, but engine continuation, changes and observations in Position details. Selecting a moment only changes the ply. Its engine line is rooted before the move while “Show position” navigates after it. [AnalysisPanel.tsx](/home/carl/projects/chess-workbench/src/components/AnalysisPanel.tsx) renders a PV as plain text, after Engine and Depth. On initial load, FEN setup and the PGN textarea precede analysis. The main line sits below all review cards, whose full PVs can be lengthy.

**Effect:** The user must remember which move they are investigating, switch tabs to find its consequence, mentally reconstruct a line and navigate backwards to try an alternative. Useful capabilities exist but are separated at exactly the point they should cooperate. Initial screen space explains formats and setup rather than what useful result the app can produce.

**Direction:** Keep one active review moment beside the board, with labelled “Before,” “Played move,” “Opponent response” and “Alternative” actions. Keep compact game navigation and the review queue available in that context. Put full engine diagnostics and exhaustive material counts behind details. Shorten the default continuation to the meaningful first few moves and make the rest expandable and playable. Collapse setup once successful in standalone mode too.

Milestone 9 improved scrolling and setup clutter; retain those gains. Its specification deliberately preserved chess semantics and existing panel content. Another layout-only pass cannot resolve the learning gap.

**Validation:** Test the unified investigation view before removing the existing tabs wholesale. The goal is fewer context changes, not fewer clicks at any cost.

### 5. Engine evidence has no clear lifecycle from quick scan to trusted explanation

**Type:** technical support for a product trust problem. **Confidence:** high for inconsistent presentation; reliability impact needs measurement.

**Evidence:** [types.ts](/home/carl/projects/chess-workbench/src/engine/types.ts) uses 500 ms for each batch position and 1,500 ms for selected positions. [useWorkbenchAnalysis.ts](/home/carl/projects/chess-workbench/src/engine/useWorkbenchAnalysis.ts) retains batch results separately and resumes selected-position analysis afterwards. The toolbar reads retained batch results while Position details reads current analysis. I observed the toolbar at −0.67 while the same position's live panel showed −0.64 and later −0.70 during search. That is expected search refinement, but it is not explained. Review moments stay based on the retained quick pass. Starting another batch clears its old results; cancellation retains partial results, but there is no resume action.

The ranking uses adjacent searches with potentially different achieved depths. A 75-centipawn threshold is not a confidence estimate. The client also submits each position as `position fen ...`, without preceding moves ([stockfishAnalysisClient.ts](/home/carl/projects/chess-workbench/src/engine/stockfishAnalysisClient.ts:274)); repetition context therefore is not supplied. This last point is a technical limitation to cover before stronger draw-related explanations, not a demonstrated cause of the owner's dissatisfaction.

**Effect:** The same position can appear to have two answers, and a confident-sounding review sentence can outlive the evidence used to create it. Repeated scans consume time without moving the user forward. An 80-ply game has 81 scheduled searches, or about 40.5 seconds of nominal search budget before overhead; this is calculated, not a measured device benchmark.

**Direction:** Distinguish quick candidates from inspected moments. When opening a moment, deepen its relevant before/after evidence using a consistent policy, keep the previous complete result visible as provisional and publish a coherent replacement. Use one explicit source for the displayed review score pair. Keep live exploration scores labelled separately. Preserve completed work on cancellation and offer resume. Reuse results where the request identity and analysis policy match. Keep one Worker.

**Validation:** Measure shortlist stability and time to the first useful explanation on representative hardware. Do not claim stronger search guarantees truth or create a numerical confidence percentage without a justified model.

### 6. The session has no lasting output or return path

**Type:** product/workflow omission. **Confidence:** high about absence; medium about retention benefit.

**Evidence:** [Architecture](/home/carl/projects/chess-workbench/docs/architecture.md) explicitly states no persistence. `App` initialises from the starting position with empty PGN. There are no saved moments, notes, completed-review state or export controls. Imported comments and annotations are accepted but not displayed. The product document places local saving in an optional later phase.

**Effect:** Closing the session discards its value unless the user records it elsewhere. Returning means fetching the same input and repeating analysis. There is no way to answer “what did I learn last time?” or eventually recognise a recurring mistake.

**Direction:** Move a small amount of local continuity earlier: resume the last game/ply and save selected moments with an optional takeaway. Start with an explicit local save/restore and exportable record, not accounts, cloud sync or a spaced-repetition platform. Preserve source PGN alongside notes; do not overwrite its existing annotations.

**Validation:** First ask the owner to record a takeaway manually during prototype sessions. If they do not want to revisit it, session restore may be sufficient; do not build a lesson library on assumption alone.

### 7. Getting to the useful work requires avoidable setup and navigation effort

**Type:** UX and discoverability. **Confidence:** high about available controls; priority within this group needs owner input.

**Evidence:** The opening instruction is “Load a position or move a piece to explore the board.” The available import UI is a FEN field and a pasted-PGN textarea; there is no sample, file chooser or export guidance. Loading a game then requires a separate analysis action. [PositionBoard.tsx](/home/carl/projects/chess-workbench/src/components/PositionBoard.tsx) fixes orientation to White and wires piece drops, with no app-level click-to-move interaction or legal-destination cues. Game navigation uses buttons without global arrow-key handling. Narrow-screen selection does successfully reveal and focus the board, but the board and investigation text remain vertically separated.

**Effect:** The user has to know formats, retrieve data and orchestrate analysis before discovering the benefit. Reviewing Black is needlessly less natural. Repeated pointer actions and board/text travel make investigation slower. These costs matter particularly because a competing tool may already contain the game.

**Direction:** Offer a primary “Review a game” entry with paste, single-file import and a short example; keep “Explore a position” available. Make “Load and review” start the intended pass with progress and cancellation, while retaining a navigation-only option. Add board flip, click-to-move and scoped Left/Right navigation that does not intercept typing. Put current move and investigation controls next to the board at narrow widths. Account-linked automatic game retrieval should wait until the owner's actual source and frequency justify it.

**Validation:** Observe the owner's real path from finishing a game to opening this app. PGN export may be the largest barrier, or it may be trivial for their workflow. Do not automatically introduce service integrations to save a rarely used action.

### 8. Verification protects implementation contracts more than successful learning

**Type:** development process and technical validation. **Confidence:** high.

**Evidence:** The 193 tests cover valuable edge cases: special moves, pinned attack-map semantics, PGN handling, score signs, cancellation and stale results. Application tests also intentionally protect exiting review on a board move. Board interaction is mocked in [App.test.tsx](/home/carl/projects/chess-workbench/src/App.test.tsx:12), and most engine integration tests use fakes. Milestone/journal acceptance is largely about correct panels and lifecycle behaviour; the product's “regularly choose this tool” criterion remains unmeasured.

**Effect:** A fully green suite can preserve a frustrating product. Unit tests cannot show whether somebody understood why a move was bad or could complete an investigation without losing their place.

**Direction:** Keep the existing tests, changing deliberate old contracts when the workflow changes. Add a few meaningful end-to-end scenarios covering import → moment → alternative → return, plus restore. Run real-engine smoke checks without exact-score assertions. Add short owner sessions with observed learning outcomes as a release gate for the next product milestone.

**Validation:** Establish a baseline now; do not claim a new panel improves learning simply because it renders correctly.

## 4. Architecture assessment

The stack is not the obstacle. React state, plain TypeScript domain functions, immutable parsed games and one Worker are appropriate. Separation of UCI from React, matching results by request/FEN, cancellation generations and static insights surviving engine failure are assets. Preserve them. No backend, router, global state library or generic plugin architecture is needed for the proposed next step.

Three boundaries need deliberate adjustment:

1. **Game ownership versus displayed position.** The current exclusive workspace makes changing the board equivalent to leaving the game. Retain a game session independently of its active exploration line. Still derive exactly one displayed FEN; do not introduce competing board authorities.
2. **Engine data versus rendered notation.** Analysis types retain the PV mainly as a SAN string. Preserve structured moves and their root FEN through the engine/domain boundary for safe replay. The existing coordinate-to-SAN replay logic is a useful starting point; do not parse display prose back into moves.
3. **Background scan versus active investigation.** The hook currently lets a batch own the Worker until completion/cancellation. A selected moment should be able to request focused work without losing the batch's completed entries. Implement explicit, small scheduling rules and retain generation guards; do not create a second engine to bypass coordination.

A small pure workspace transition module or reducer would become useful for exploration, return and restore. Extract it because these transitions need testing, not because `App.tsx` must meet a size target. Existing insight calculations can remain separate, but presentation needs a composed review model that ties a finding to a move, evidence line and board state.

### Concrete implementation briefs

#### A. Safe exploration — first coding milestone

**Scope:** `App`, the workspace domain/state transitions, board controls, engine-hook integration and relevant tests.

- Retain an immutable imported game, source ply and analysis identity during exploration. Add one temporary line containing a root position, applied moves/position snapshots and a cursor. A move after undo replaces only the temporary future.
- Derive the displayed FEN from the line cursor or selected game ply. Every position consumer must use it. A branch FEN must never be presented with the source ply's retained evaluation.
- Expose Previous/Next within the temporary line, Reset line and Return to game. Return restores the source ply and review context without importing or scanning again. Game navigation deliberately exits the temporary line while retaining the game.
- Use the same line-history behaviour for standalone exploration. Preserve promotion/cancellation semantics and invalid-input behaviour.
- Keep the original game identity supplied to analysis. Separate “displayed position belongs to this game ply” from “a game is retained”; use a null game-position index during a branch. Verify background results cannot bleed into branch analysis. Initially keeping the existing batch ownership policy is acceptable if its waiting state is explicit.
- Replace tests asserting destructive exit with behavioural tests for return, undo, branching after undo, promotion, analysis preservation and replacing a game. Update architecture documentation to describe the new boundary.

**Acceptance:** Load and analyse the diagnostic PGN, go before `g4`, try at least two moves, undo and return. The same game, selected source move and completed scan remain available. Standalone moves are reversible. No new dependency is needed.

#### B. Understand one moment — second milestone, after A

**Scope:** review presentation, structured line data, chess replay helpers and active investigation state.

- Preserve coordinate PV moves alongside root FEN and SAN display text in typed engine results. Validate replay through the chess boundary, including castling and promotion; mark truncated/invalid lines rather than inventing moves.
- Give a moment an explicit pre-move root and played move. Present Before, Played move, Show response and Explore alternative. Use the post-move PV for the opponent response and the pre-move PV for the alternative; label them distinctly.
- Show one active moment and a compact queue. Keep its identity visible when changing board states. Put the relevant consequence first; make raw evaluation/depth and static inventories supplementary.
- Use a few verified explanation cases initially, including immediate mate, with an honest fallback for unsupported positions. Do not automatically treat a loose-piece warning as the cause of score loss.
- Add selected-side preference before shortlist truncation and a manual “Review this move” action. Do not introduce a new global ranking formula in this slice.

**Acceptance:** For `g4`, one action demonstrates `...Qh4#`; another returns to the pre-move board and shows an alternative. The owner can explore either line and return without losing the moment. An unsupported positional case still offers correct evidence without pretending to explain it. Test both colours and custom-FEN PGNs.

#### C. Consistent review evidence — supporting milestone

**Scope:** engine types/hook and pure review derivation; retain the UCI client boundary.

- Add provenance for search budget/quality policy and keep quick-pass versus focused results explicit. Retain an inspected moment's before/after pair as a coherent snapshot.
- On opening a candidate, schedule bounded refinement of the relevant positions. Publish the new pair together, with a visible pending state and a clear message if the original finding changes. Do not repeatedly reorder the active review while the user is reading it.
- Use the same settled pair in the review card and its review evaluation display. Live branch evaluation remains separate and labelled.
- Resume a cancelled scan from missing entries; keep completed evidence visible during replacement work. Add an explicit engine retry path that preserves the session after terminal Worker failure.
- Preserve request IDs, root identity and generation checks. Test rapid navigation, a branch during scanning, cancellation, game replacement and late responses.

**Acceptance:** There are no unexplained competing review scores for the same evidence snapshot. Cancellation/resume does not repeat completed entries. A finding withdrawn after refinement is communicated honestly. No exact-score assertions against real Stockfish.

#### D. Make returning worthwhile — small follow-on, gated on owner use

- Store one versioned local session: source PGN, player side, selected ply and explicitly saved takeaways. Validate restored data through existing parsers. Add an explicit reset/delete action and tolerate unavailable/corrupt storage.
- Save a moment's root FEN, move identity and optional note. If retaining engine evidence, include engine version/search policy and label it as saved evidence; never restore a running job as running.
- Offer a simple portable export. Avoid accounts, multi-device sync and broad archives.

**Acceptance:** Reloading can restore the review location and a saved takeaway. A malformed saved record cannot prevent startup. Loading a new game cannot attach old notes to its positions.

### Validation before expanding the roadmap

Use five recent owner games, including both colours, plus two positions they found difficult to understand in their usual tool. Observe the current baseline and the proposed workflow on comparable material. Record time to a useful position, lost-context events, unnecessary tool switching and whether the owner can explain the lesson without reading the screen.

Proposed product acceptance: in a short session the owner can identify a useful decision, demonstrate its consequence, test an alternative and state a takeaway without restarting or using another analysis tool. Then see whether they voluntarily choose Chess Workbench for several subsequent real sessions. These are proposed acceptance criteria, not measured results or a demand for telemetry.

If understanding improves but importing remains the reason they avoid it, prioritise source-specific import. If they prefer investigating single positions, change the entry workflow accordingly. If neither experience is preferable, stop expanding the roadmap and identify the missing value with the owner.

Defer a broad tactical detector catalogue, MultiPV dashboards, accuracy grades, evaluation graphs, automatic recurring-pattern analysis, account integration and LLM commentary until they solve an observed obstacle in that session. Some may eventually be useful; none repairs destructive exploration by itself.

## 6. Minor polish and verification notes

Secondary issues worth bundling with related work:

- Board flip is a usability requirement for reviewing Black, not cosmetic polish. By contrast, colour/theme redesign is low priority.
- “Plies,” “500 ms per position,” material totals such as `39–39` and `M0` assume familiarity or expose implementation detail. Prefer move context and explicit terminal status in primary presentation. The diagnostic game ends with `M0`; “Black wins by checkmate” would be clearer.
- “What changed?” refers to a static rule “above,” although the insights panel is rendered later. Fix the reference and make empty-state wording specific to the current task. At a game's starting position, telling the user to make a board move currently directs them out of review.
- The tabs have ARIA roles but no conventional arrow-key behaviour. Promotion has initial focus and Escape handling but no explicit focus trap/return. Address keyboard behaviour alongside the new investigation controls and test the real board, not only mocks.
- The README introduction still describes the early FEN/one-line engine application. Update it with the actual review workflow and an example once the next direction is accepted.

- `npm run verify` passed: formatting, ESLint, **193 tests in 17 files**, TypeScript and production build.
- Real Stockfish completed the five-position diagnostic game in both deployed and local browser sessions. The main finding and disconnected detail panels reproduced locally. Deployed browser interaction confirmed the destructive alternative-move transition and loss of scan results after reimport.
- Narrow-screen selection revealed/focused the board as intended. This was a limited responsive check, not a complete mobile, touch or assistive-technology audit. Long-game timing, engine-failure recovery in the browser and real-user learning outcomes were not measured.
